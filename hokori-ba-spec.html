Hokori: AI Package Governance, Shared Quota & Learner Rules

Project Hokori — AI-Powered Japanese Learning Web Platform (Capstone FA25SE183) Author / Role Dang Duc Anh (BA documentation & Front-end; team document)
Scope Learner AI Quota, Admin AI Package CRUD, JLPT & Enrollment Guards Document Note Structured in English for Portfolio review from the original Capstone business rules, with test scenarios derived from them

1. Business Decision: Shared AI Quota Architecture

Problem Statement: Hokori offers multiple AI study tools (Sentence Grammar Analysis, AI Kaiwa Pronunciation Scoring, and AI Conversation). Splitting quotas per individual AI service created complex pricing tiers, confusing UX for learners, and unnecessary per-service tracking overhead on the back-end.

Finalized Decision (Shared Credit Pool): Each AI package defines exactly three core attributes: TOTAL_AI_QUOTA (shared credit pool), duration (validity in days), and price. Every invocation of any AI feature deducts 1 shared credit with no service-specific multiplier.
Layer Cross-Functional Implementation Impact
Backend API Maintains a single quota counter per active package purchase; eliminates per-service_code quota branching and simplifies atomic deduction.
Frontend (Learner) Displays one clear metric (Remaining AI Credits) in Header & AiQuotaOverview, reducing cognitive load during study sessions.
Admin Portal Streamlines package creation to a single TOTAL_AI_QUOTA input field with built-in form validation before publishing.

2. Admin AI Package CRUD & Commercial Fairness Rules

Core Principle (Locked Contract): Once an AI package has been purchased (purchase_count > 0) or consumed (usage_count > 0), it represents an active commercial agreement. Administrators must never retroactively alter its price, quota, or duration. Any pricing or promotional update requires creating a new AI package while existing buyers retain their terms.

Rule ID Action Allowed Condition Blocked Condition & System Behavior
RULE-01 Edit Package Status = INACTIVE AND purchase_count = 0 AND usage_count = 0. Blocked if ACTIVE OR purchased/used. Admin UI disables edit controls and explains immutability.
RULE-02 Deactivate Status = ACTIVE AND purchase_count = 0 AND usage_count = 0. Cannot deactivate-to-edit once purchased/used; Admin must create a new package for changes.
RULE-03 Activate Status = INACTIVE AND unused (purchase_count = 0, usage_count = 0). Prevents reactivating retired legacy packages with historical purchase records.
RULE-04 Delete purchase_count = 0 AND usage_count = 0 (soft-delete preferred). Hard/soft delete strictly blocked if any buyer or usage history exists, preserving audit trail.

3. Sample User Stories & Acceptance Criteria (Given / When / Then)

US-AI-01: Enforce Shared AI Quota Gating for Learners (Traces to BR-LR-17, BR-LR-18)

As a Learner, I want to see my remaining shared AI credits and be clearly notified when my quota reaches zero so I know when to renew my AI package.

  • AC1 (Deduction): Given an authenticated Learner with an active AI package (remaining_quota > 0), When they submit an AI Kaiwa recording or Sentence Analysis request, Then the system returns AI feedback and decrements remaining_quota by exactly 1 across all UI displays.
  • AC2 (Zero-Quota Block): Given a Learner with remaining_quota = 0 or an expired package, When they attempt to invoke any AI feature, Then the API blocks the request and the UI prompts the AiPackageModal to purchase/renew a package.
US-ADM-02: Protect Purchased AI Packages from Retroactive Edits (Traces to RULE-01, RULE-04)

As an Administrator, I want the system to prevent editing or deleting AI packages that already have buyers so existing learners’ purchased contracts remain fair and auditable.

  • AC1 (Unlocked Package): Given an INACTIVE AI package with purchase_count = 0 and usage_count = 0, When Admin updates price/quota/duration and saves, Then the system validates inputs and persists the update.
  • AC2 (Locked Package): Given an AI package with purchase_count ≥ 1, When Admin attempts to edit or delete it, Then the system rejects the mutation with a clear message instructing Admin to create a new package instead.
